# Helpes — внутренняя система заявок технической службы

MVP для компании «Кыргыз Алтын». Сотрудник без входа отправляет заявку о неисправности
с телефона или компьютера; техники видят общую очередь и берут заявки в работу; администратор
управляет пользователями, назначениями, этажами, кабинетами и категориями.

> Статус: исходный код и тесты готовы. Приложение **не развёрнуто** ни на каком сервере компании —
> это отдельный шаг, см. [docs/DEPLOY.md](docs/DEPLOY.md).

Сквозной процесс: **сотрудник отправляет заявку → она в очереди → техник берёт или администратор
назначает → ремонт → результат и статус сохраняются в истории.**

## Стек и архитектура

Django 5.2 LTS (монолит) · Django Templates · Bootstrap 5 (лежит в `static/vendor/`, интернет на клиентах
не нужен) · PostgreSQL (целевая БД) / SQLite (локальная разработка) · WhiteNoise для статики · Gunicorn.

```
config/            настройки (через переменные окружения), urls, wsgi
tickets/
  models.py        Building, Floor, Location, EquipmentCategory, Ticket, TicketItem, TicketComment, TicketHistory
  services.py      вся бизнес-логика: создание, взять/вернуть/назначить, смена статуса, переоткрытие, массовая передача
  permissions.py   роли (группы «Техники» и «Администраторы») и декораторы доступа
  forms.py         серверная валидация
  views_public.py  открытая форма сотрудника
  views_staff.py   очередь и карточка заявки (техник и админ)
  views_panel.py   панель администратора: назначения, пользователи, справочники
  seed.py          стартовые категории и группы (применяются миграцией 0002)
  tests/           68 функциональных тестов + 2 теста реальной параллельности (PostgreSQL)
docs/              руководство администратора, развёртывание, предположения
scripts/           backup.sh, restore.sh
```

Три интерфейса:

| Интерфейс | URL | Доступ |
|---|---|---|
| Сотрудник | `/` | без входа |
| Техник | `/staff/` | вход, роль «Техник» |
| Администратор | `/panel/`, `/staff/` | вход, роль «Администратор» |

Жизненный цикл: **Новая → В работе ⇄ Ожидает → Выполнена**. Статус и исполнитель хранятся раздельно.
Свободная заявка = открытая и без исполнителя (её статус всегда «Новая»).

Защита от двойного взятия: «Взять в работу» — один условный `UPDATE … WHERE assignee IS NULL`;
БД гарантирует, что успешным будет ровно один запрос. Остальные операции берут блокировку строки
(`SELECT … FOR UPDATE`).

## Быстрый старт (локальная разработка)

Нужен Python 3.10+.

```bash
python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                 # Windows: copy .env.example .env  (по умолчанию SQLite, DEBUG=1)
python manage.py migrate             # создаёт таблицы, группы ролей и стартовые категории
python manage.py createsuperuser     # первый администратор
python manage.py runserver
```

Откройте http://127.0.0.1:8000/ (форма сотрудника) и http://127.0.0.1:8000/login/ (служебный вход).
Суперпользователь, созданный через `createsuperuser`, автоматически считается администратором.
Дальше техников создаёт сам администратор в разделе «Пользователи».

Если `DJANGO_DEBUG=0`, приложение откажется запускаться без `DJANGO_SECRET_KEY`.

## Тесты

```bash
python manage.py test tickets                      # SQLite, 68 тестов (+2 пропускаются)
# на PostgreSQL (включая тест настоящей параллельности):
DB_ENGINE=postgres DB_PASSWORD=... python manage.py test tickets
```

Для PostgreSQL у пользователя БД должно быть право `CREATEDB` (Django создаёт временную тестовую базу).

## Настройки (переменные окружения)

См. `.env.example`: `DJANGO_SECRET_KEY`, `DJANGO_DEBUG`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`,
`DJANGO_SECURE_COOKIES`, `DB_*`, `HELPES_STALE_HOURS` (по умолчанию 48 ч), `HELPES_RATE_LIMIT_*` (антиспам формы).
